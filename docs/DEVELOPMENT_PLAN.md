# ExhibitIQ 開發計畫

> 版本：V2.5（2026-11-04；Eric 核定動態分析設定：不限定 BXR 或任何產業、三種分析模式、9 個主選單、A2-15～A2-17、W2-06。前版 V2.3：2026-11-03；移除特定展覽依賴。前版 V2.2：2026-11-03；通用展覽平台定位、Dashboard 必要模組、通用性驗收。由 data 經專案負責人特別授權修訂，不改變模組所有權）｜負責人：專案負責人（`ai`）
> **這是四個階段唯一的工作清單。** 原則、架構與契約以 [`ExhibitIQ_專案總規範.md`](ExhibitIQ_專案總規範.md) 為準；目錄負責人以 [`architecture/module-boundaries.md`](architecture/module-boundaries.md) 為準；目前進度記錄在 [`PROGRESS.md`](PROGRESS.md)。三者衝突時，以總規範為準，並修正本文件。

## 1. 怎麼使用這份計畫

- 每個工作項目有一個編號：`A`＝AI（專案負責人）、`W`＝Web Dashboard（專案負責人）、`D`＝Data（同事）；數字是 Phase。
- 一般工作**不需要建立 GitHub Issue**，直接依本計畫的編號開發。Issue 只用於：Bug、重大需求變更、跨人協調、需要追蹤的問題。
- 分支：`feature/<ai|data>/<編號小寫>-<slug>`，例如 `feature/ai/w1-01-frontend-scaffold`。PR 標題格式：`【Eric 合併】[A1-06] …` 或 `【Albert 合併】[D1-05] …`（合併人規則見 [`workflow/branching.md`](workflow/branching.md)）。
- 每個可以獨立驗收的工作項目建立一個 PR，base 是自己的 dev 分支；**測試通過後由各自的 Claude Code 自行合併**（V2.4）。
- **各自連續往下做，不等對方：** Phase 是檢查點，不是關卡；跨人的銜接只透過 `schemas/` 契約與範例資料，需要對方配合時才開協調 Issue。
- 依賴欄寫的是**真正需要先完成的項目**；沒有依賴的項目可以平行進行。
- 本計畫的項目只能由專案負責人新增、刪除或改變負責人。
- **ExhibitIQ 是通用型展會情報平台**（總規範 §1.1）。**嚴禁將任何特定展覽列為預設開發目標、主要資料來源、必要驗收對象或專案負責人必須指定的測試案例。** 工作項目寫的是通用能力；測試來源由資料工程依公開資料的可取得性自行挑選；單一展覽取得失敗只記錄原因並改用其他來源，不阻礙任何工作項目或階段。

## 2. 系統模組與分工

| 模組 | 負責人 | 內容 | 主要路徑 |
|---|---|---|---|
| Data Platform | data | 爬蟲、匯入、ETL、驗證程式、資料包、資料集索引、資料品質、GitHub Actions | `crawler/`、`etl/`、`data/`、`.github/workflows/`、`tests/data/` |
| AI Intelligence | ai | 契約（`schemas/`）、Skill、分析、產品知識庫、分類、分析結果與報告 | `schemas/`、`skills/`、`knowledge/`、`reports/`、`tests/contract/` |
| Web Dashboard | ai | 前端應用：設計系統、共用元件、頁面、資料存取層、前端測試 | `site/` |

**介面：** 同事的輸出是資料包與資料集索引；AI 的輸出是分析結果；Dashboard 只讀取這些有 Schema 的檔案。前端的建置、預覽與發布 workflow 放在 `.github/workflows/`，由 data 負責。

## 3. Web Dashboard 架構

Web Dashboard 是**競賽 MVP 的必要模組**：一個可以操作、搜尋、篩選、查看分析、比較資料與匯出報告的網頁系統。

| 項目 | 決定 |
|---|---|
| 形式 | 靜態 SPA，不需要後端或常駐服務。新增展覽、觸發擷取、執行分析等後端任務經 GitHub Actions 手動執行與 Claude Code 工作階段完成，網頁只產生請求內容並提供連結（總規範 §4.1）；網頁一鍵執行需專案負責人核准新服務 |
| 技術 | React + Vite + TypeScript；Ant Design 5（`zh_TW` 語系、主題 token）；Apache ECharts；React Router（HashRouter）；Vitest；Playwright |
| 型別 | 由 `schemas/` 產生 TypeScript 型別，前端不另寫一份 |
| 資料流 | 資料包、資料集索引、分析結果、產品知識庫 → `site/` 內的 bundle 產生程式（確定性，不用 AI；先驗證 Schema，不合格就停止）→ `bundle.json` → `site/src/data/` Repository 介面 → 頁面 |
| 頁面與原始資料 | 頁面只呼叫 Repository 介面，不直接讀資料包或爬蟲格式 |
| 語系 | 繁體中文優先；介面文字集中在 i18n 檔，預留英文 |
| 報告 | 網頁與 PDF 使用同一份分析結果 JSON 和同一個 `ReportViewer` 元件；PDF 由列印樣式產生 |
| 安全 | 前端不放任何 Token、API Key 或可寫入憑證；「新增展覽」「手動執行」只產生內容並連到 GitHub Actions 頁面；公開版打包有白名單檢查 |
| 通用性 | 頁面、導覽與元件不得寫死任何展覽的名稱、ID 或欄位；展覽清單一律來自資料集索引 |
| 預覽 | Actions build artifact（單一 HTML，私有）、雲端 `vite preview`、Playwright 截圖。**GitHub Pages 網站是公開的**，只能放專案負責人核准的非機密內容 |

**主選單（9 項）：** 系統總覽、展覽搜尋與新增、展覽情報與比較、參展商與企業情報、商機分析與評分、BXR 產品推薦、AI 報告中心、分析設定、資料及系統狀態。V2.5 新增「分析設定」是全系統共用功能（分析模式、主題、關鍵字、分類與同義詞、企業關係規則、評分模型、設定匯入／匯出），不是商機分析的附屬功能。**PDF／CSV 匯出**是跨頁共用功能（表格匯出 CSV、報告匯出 PDF），不另設頁面。

**共用元件（只維護一份，放在 `site/src/components/`）：** 設計 token、`AppLayout`／`SideNav`／`TopHeader`／`PageHeader`、`DataOriginBanner`、`KpiCard`、`DataTable`、`FilterBar`／`SearchBox`、`ChartPanel`、`ClaimBadge`、`StatusBadge`、`CompletenessIndicator`、`SourceRef`、`ScoreBreakdown`、`ReportViewer`、`LoadingState`／`EmptyState`／`ErrorState`。頁面只能組合這些元件，不能各自設計樣式或表格。

**顯示規則：**
- 每一頁都標示資料是真實（`collected`）還是合成（`synthetic`）。
- AI 推論一律用 `ClaimBadge` 標示，不和來源事實混在一起顯示。
- 評分必須能拆解到各項因子與來源；沒有依據的因子不計分。
- 完整度不是 `complete` 時，相關數字旁邊要顯示完整度；沒有資料時顯示「資料不足」或「未知」，不得以推測補足。
- 後續 Phase 都在同一個網站上擴充，不另做 Demo。

**動態分析設定（V2.5，[`specs/analysis-profile-contract.md`](specs/analysis-profile-contract.md)）：**
- ExhibitIQ 不限定 BXR 產品或任何產業。分析主題、關鍵字、產業範圍與目的由使用者設定；任何主題或關鍵字都不得寫死為唯一方向。
- 三種模式：A. BXR 商機分析、B. 產業與技術研究、C. 競爭對手研究。**B、C 不得依賴 BXR 產品卡。**
- 設定有三種狀態，畫面必須清楚區分：**本機草稿**（瀏覽器）、**已提交**（`knowledge/analysis-profiles/`）、**已產生分析結果**（分析結果的 `analysis_config`）。修改本機關鍵字不會改變雲端分析結果。靜態網站不執行分析：分析由雲端 Claude Code 工作階段（日後可改 Actions）讀取已提交的設定執行。
- 企業關係為多標籤；關鍵字命中只是候選訊號，不是事實。商機評分只用於有商業目的的設定，權重可調整；不以「展位已公布」加分。

## 5. 每個 Phase 的共同交付

每個 Phase 結束時，都要交付：

1. 可以在瀏覽器操作的 Dashboard 版本（Actions artifact 或雲端預覽）
2. 本階段完成的功能清單
3. 實際畫面截圖（桌機與手機）
4. 對應的 PR 連結
5. 測試結果
6. 已知限制
7. 下一階段要新增的功能
8. 哪些資料是真實資料、哪些是合成資料
9. 本階段的通用性驗收結果（§6）

**不能只用 Markdown 文件、終端機輸出或測試通過，取代瀏覽器上的成果。**

## 6. 通用性驗收

**必要驗收：在不修改核心程式的前提下，系統能處理另一個不同展覽的資料，完成標準化、AI 分析及 Dashboard 展示**（總規範 §8.1）。

| 階段 | 通用性檢查 | 資料要求 |
|---|---|---|
| Phase 1 | 使用兩組不同結構的合成展覽資料，驗證 Schema、資料流程與 Dashboard；核心程式沒有寫死展覽 | 合成資料（D1-06），標示 `synthetic` |
| Phase 2 | 驗證通用資料蒐集、匯入、AI 分析及前端呈現：兩組不同結構的展覽資料走同一套標準化 → 資料包 → AI 分析 → Dashboard 流程，第二組資料的 PR 不修改核心程式 | 測試來源由資料工程依公開資料的可取得性自行挑選合法來源，不需要專案負責人指定展覽；取得失敗的來源記錄後改用其他來源，不列為阻礙 |
| Phase 3 | 在 Dashboard 搜尋或新增此前未收錄的展覽，經通用流程（登錄 → 來源探索與評估 → Actions 擷取或匯入 → 標準化 → 分析）完成資料處理、比較與報告匯出 | 真實公開資料優先；資料不足時明確標示 |
| Phase 4 | 以至少兩組不同結構的展覽資料完成端到端驗證；檢查核心程式中沒有寫死展覽（測試強制） | 至少一組真實、合法取得的公開資料 |

**驗收的是可重用的系統能力，不是完成特定展覽的名單；任何展覽的參展商數量都不是驗收指標。**

**動態分析設定驗收（V2.5，Phase 2～3）：** ① 同一個展覽可以套用不同主題與模式並保留不同分析結果；② 使用者可以自行新增、刪除關鍵字；③ 修改關鍵字不需要修改核心程式；④ 不使用 BXR 產品資料也能執行產業研究；⑤ 同一企業可以同時符合多種關係；⑥ 每份分析報告都能追溯使用的關鍵字、分析模式、資料來源與版本；⑦ 系統不把關鍵字命中當成已確認的事實。

**「核心程式」的範圍：** `etl/` 的標準化與驗證程式、`schemas/`、`skills/` 的分析邏輯、`site/` 的頁面與元件。**可以為新展覽新增或修改的：** 展覽登錄資料、`crawler/` 的來源設定與來源適配器、匯入欄位對應設定、資料檔。

**資料取得結果都必須被處理：** 自動擷取、半自動、檔案匯入、人工輸入、部分成功（`partial`）、無法確認完整度（`unknown`）、取得失敗。每一種結果在資料集索引與 Dashboard 上都看得到，不得宣稱所有展覽都能自動取得完整資料。
