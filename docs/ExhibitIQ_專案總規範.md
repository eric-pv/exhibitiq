## 1. 專案目的與邊界

**ExhibitIQ 是可支援不同展覽的通用型 AI 展會情報搜尋、蒐集、分析與可視化平台**，由全球動力科技（Big x Reality）為內部 AI 應用實戰挑戰賽開發。它不是任何單一展覽的專用系統。**真正的 AI 功能發生在使用 Claude Code Skill 分析資料時**，不只是以 AI 協助撰寫程式。

使用者應能：

1. 搜尋已登錄的展覽，或新增一個展覽（提供展覽名稱、國家、年份或官方網站）。
2. 探索該展覽可用的資料來源，並評估取得方式與限制。
3. 擷取或匯入參展商及相關資訊（自動擷取、半自動、檔案匯入或人工輸入）。
4. 透過共用 Schema（`schemas/`）標準化資料，保存來源與歷史。
5. 執行 AI 企業情報、商機、競品、合作及 BXR 產品適配分析。
6. 在 **Web Dashboard** 查看結果；比較不同展覽及年度；匯出 PDF／CSV 報告。

### 1.1 通用性原則（不可改寫）

- **任何特定展覽都只能是測試案例。** 核心程式、Schema、分析邏輯、Dashboard 頁面與導覽不得寫死特定展覽的名稱、ID、網址、欄位或筆數；展覽相關的差異只能放在來源設定（例如 `crawler/` 的來源設定檔）、來源適配器或匯入對應設定中。
- **新增一個展覽不應需要修改核心程式**：只需要新增展覽登錄資料、來源設定或適配器，或匯入檔案；之後的標準化、AI 分析與 Dashboard 呈現沿用同一套流程。
- **不保證每個展覽都能自動取得完整資料。** 每個展覽的資料取得都要經過來源評估，並允許以下結果：自動擷取、半自動擷取、檔案匯入、人工輸入、部分成功（`completeness_status: partial`）、無法確認完整度（`unknown`）或取得失敗。資料不足時，Dashboard 與報告必須明確顯示「資料不足／未知」，不得以推測補足。
- **強制規則：ExhibitIQ 嚴禁將任何特定展覽列為預設開發目標、主要資料來源、必要驗收對象或專案負責人必須指定的測試案例。所有展覽資料來源均由通用探索與評估流程決定。特定展覽的取得失敗，不得阻礙通用系統繼續開發。**
- 測試用的展覽與來源由資料工程依公開資料的可取得性與合法性自行挑選；某個來源無法取得時，記錄失敗原因（資料集索引、來源評估報告）並改用其他來源。
- 任何展覽的參展商數量都不是驗收指標；驗收的是可重用的系統能力。
- 過去針對特定展覽的來源評估（`docs/data-platform/` 中的評估報告）只保留為**歷史紀錄**，不是後續工作的依賴。

**優先順序：** 可運作、可驗證、可重複使用、可展示 > 完整商業級介面與基礎設施。沒有證據不得宣稱已取得完整參展名單或完成準確市場預測。

## 2. 唯一確定的工作流程（不可改寫）

- **你（專案負責人）**：負責架構決策、AI Skill、產品知識、分析、報告及 Web Dashboard；每個自己的工作項目自行透過 ChatGPT 產生 Claude Code 指令、自行執行、自行確認並合併自己的功能 PR 到 `dev/ai-intelligence`。**每個階段兩人的項目全部完成後，由你驗收、向 ChatGPT 索取該階段整合指令，交給 Claude Code 執行整合、測試並決定是否進入下一階段。**
- **同事（資料工程負責人）**：負責爬蟲、來源評估與適配、匯入、ETL、GitHub 資料儲存與自動化（GitHub Actions）、資料品質。每個自己的工作項目自行透過自己的 ChatGPT 產生 Claude Code 指令、自行執行、自行確認並合併自己的功能 PR 到 `dev/data-platform`。**不負責你的 PR，不負責階段整合與最終驗收。**
- **兩邊的 ChatGPT**：根據本文件、`CLAUDE.md`、[`DEVELOPMENT_PLAN.md`](DEVELOPMENT_PLAN.md) 中的工作項目和最新 Repo 狀態，將**一個工作項目**轉成可直接交給 Claude Code 的完整指令；不擅自變更架構、跨越他人負責範圍或假設不存在的檔案。
- **兩邊的 Claude Code**：在雲端執行開發、測試、提交、建立 PR；依指令把 PR 的 **base 設為自己的長期開發分支**。任務擁有者自己合併 PR。不得把日常功能 PR 指向 `main`。
- **階段整合**：只有當雙方該階段所有工作都完成、PR 已各自合併至各自的開發主線後才啟動。你檢查 PR／測試紀錄，讓 ChatGPT 根據兩條分支現況產生整合指令；Claude Code 在 `integration/phase-N` 整合兩條開發線，處理衝突並執行端到端驗證。你驗收通過後才合併到 `main`，然後以整合後的 `main` 同步下一階段的兩條開發主線。

**特別強調：每個工作項目都有 PR；每個人自行合併自己的 PR；你只做每個階段完成後的整合與驗收。** 不需要你逐項審查同事的 PR。

## 3. GitHub 分支與權限

| 分支 | 用途 | 誰負責合併 |
|---|---|---|
| `main` | 僅保存各階段驗收通過的整合版本 | 你 |
| `dev/ai-intelligence` | 你的持續開發主線 | 你 |
| `dev/data-platform` | 同事的持續開發主線 | 同事 |
| `feature/ai/<工作項目編號>-<slug>` | 你的單項任務分支；PR base=`dev/ai-intelligence` | 你 |
| `feature/data/<工作項目編號>-<slug>` | 同事的單項任務分支；PR base=`dev/data-platform` | 同事 |
| `integration/phase-N` | 階段完成後的整合分支；PR base=`main` | 你 |

每項任務：開發計畫中的工作項目 → ChatGPT 指令 → Claude Code 開發與測試 → PR（可在 GitHub 前端看到）→ 任務擁有者自行合併到自己的 dev 分支 → 下一項工作。一般工作不需要建立 Issue（見 §9）。PR 需列出工作項目編號、變更檔案、測試結果、資料格式影響、已知限制。若測試未通過，先修正再合併；PR 存在不等於工作已完成。

**V2.4 獨立作業（Eric 2026-11-04 核准）：** 階段是檢查點而不是關卡，雙方各自連續往下一個 Phase 做，不互相等待；各自的 Claude Code 在測試全部通過後自行合併到自己的 `dev/*`（`main` 只由你合併）；共用檔案由 Albert 那邊開工時自行從 `dev/ai-intelligence` 取得。

**階段同步：** 完成 `integration/phase-N` → `main` 後，在方便的時點把整合後的 `main` 安全合併進兩條 `dev/*`；採用安全合併／必要時重建分支，不強制覆寫未備份的工作。若有跨分支共用 Schema 變更，先由你批准並在兩邊以相同契約實作；不必提前做程式整合。

## 4. 技術與成本原則：100% 雲端、GitHub 優先

- **唯一 Private Monorepo**：GitHub 為程式碼、規格、版本化資料及報告的中心。
- **不依賴任何人的本機運算**：兩人的電腦只用瀏覽器／遠端 Claude Code 操作。需執行 Python、測試或工具時，使用具終端機的雲端工作區（例如 GitHub Codespaces，須確認實際帳號支援 Claude Code）或 GitHub Actions。
- **GitHub Actions**：手動或排程執行爬蟲、ETL、Schema 驗證、測試、資料包生成與可公開報告的發布。排程可能延遲，Actions 並非永不停止的常駐服務。
- **GitHub 檔案式資料儲存**：JSON／JSONL／CSV／manifest，保留來源及版本。**GitHub 不是資料庫伺服器**；比賽版不導入 PostgreSQL、Supabase、常駐 FastAPI、VPS，除非你另行批准。
- 大型、頻繁變動的快照不可無限制累積在 Git history；依資料量選擇 Releases、Actions Artifacts 或日後核准的物件儲存。Actions Artifacts 可能有保留期限，不可當作唯一永久資料來源。須記錄資料包位置、雜湊、版本及取得時間。
- GitHub Pages 只能發布經你核准的非機密靜態成果；Private Repo **不代表 GitHub Pages 網站自動保密**。不可將公司敏感資料、個資、金鑰發布到公開網站。各階段的 Dashboard 私有預覽使用 GitHub Actions artifact 或雲端預覽；對外展示網址的方式由你另行核准。
- Skill 以 `skills/exhibitiq/SKILL.md`、references、scripts 組成。可在有 GitHub 存取權的 Claude Code 雲端工作環境使用；**不假設 Claude 網頁聊天會自動安裝或執行此 Skill**。
- GitHub Actions 寫入資料需使用專用受限權限與 concurrency 控制；不要讓爬蟲 workflow 自動寫入 `main` 而繞過階段驗收。比賽期間建議寫入專用資料分支／建立資料更新 PR／或保存版本化資料產物，經規定流程納入整合版本。

### 4.1 Dashboard 能直接做與不能直接做的事

Web Dashboard 是讀取版本化檔案的**靜態 SPA**。靜態網站**不能**直接執行爬蟲、寫入 GitHub、呼叫 LLM 或保存使用者輸入；不得在文件、畫面或簡報中把它描述成能直接執行所有後端任務。

| 使用者操作 | 比賽版預設做法（不需新服務） | 需要的權限 | 若要在網頁上「一鍵完成」 |
|---|---|---|---|
| 搜尋展覽 | 在 Dashboard 內搜尋**已登錄**展覽（來自資料集索引） | 無 | — |
| 探索新展覽的資料來源 | 由資料工程以 Claude Code 雲端工作階段或 Actions 進行來源評估，結果寫入文件／來源設定 | Repo 寫入權（經 PR） | 需要網路搜尋 API 與金鑰 → 新服務，需你核准 |
| 新增展覽 | Dashboard 提供新增表單，**產生**展覽登錄內容（可複製或下載），並連到 GitHub Actions 的手動執行頁面；實際登錄經 PR 進入 Repo | 操作者需有 Repo 寫入權（`workflow_dispatch`） | 需後端代理（例如 serverless 函式或 GitHub App）保管權杖 → 新服務，需你核准 |
| 觸發擷取／匯入 | 在 GitHub Actions 頁面以 `workflow_dispatch` 手動執行；輸出寫入資料分支或資料更新 PR，不直接寫入 `main` | 同上；workflow 使用最小權限 | 同上 |
| 匯入檔案（CSV／Excel／PDF） | 檔案經 PR 或 Actions 進入 Repo 後由 ETL 處理；網頁端最多只做本機預覽，不保存 | Repo 寫入權 | 需要上傳儲存 → 新服務，需你核准 |
| 執行 AI 分析 | 在 Claude Code 雲端工作階段執行 ExhibitIQ Skill，分析結果經 PR 回存，Dashboard 重新建置後顯示 | Claude Code 與 Repo 寫入權 | 在 Actions 自動呼叫 LLM 需要 API 金鑰（Secrets）與費用 → 需你核准（§10） |
| 匯出 PDF／CSV | 前端直接產生（列印樣式、CSV 下載），不需後端 | 無 | — |

**前端不得放任何 Token、API Key 或可寫入的憑證。** 任何「一鍵執行」功能都屬於架構與儲存選擇變更，必須先經你核准。

## 6. 資料契約與證據

- `schemas/` 是唯一契約來源，含 `schema_version`；修改共用欄位必須先經你核准，更新樣本、驗證器與文件。
- 區分 `exhibition`（展覽）、`edition`（屆次）、`company`（企業）、`participation`（參展紀錄）、`source`（來源）、`crawl_run`（擷取批次）、`analysis_run`（分析批次）。企業 ID 需穩定，名稱／網域／別名不可草率視為同一家公司。
- 資料包建議包含 `manifest.json`、`companies.jsonl`、`participations.jsonl`、`sources.jsonl`、`changes.jsonl`，必要時另附 BXR 產品知識與歷史分析索引。
- `manifest.json` 至少包含：`schema_version`、`dataset_id`、`exhibition_id`、`edition_year`、`created_at`、`source_snapshot_ids`、`record_counts`、`content_hash`、`completeness_status`。
- 分析結果至少包含：`analysis_id`、`input_dataset_id`、`input_hash`、`skill_version`、`generated_at`、`evidence_source_ids`、`conclusions`、`uncertainties`、`recommendations`、`review_status`；可取得時另記 model 版本。
- 爬蟲／ETL 僅執行可重現的資料整理、規則分類與初篩，不把 AI 推論寫成來源事實；初篩不可刪除原始紀錄。區分已驗證、待驗證、AI 推論、人工確認、資料不足。
- 每個市場結論都應附來源與時間；無法確認則標示未知，不得捏造企業、展位、數量、技術能力、報價、趨勢或引文。
- 任何展覽的官方或媒體公布筆數都不代表已成功取得完整名單；沒有已保存的來源時官方筆數為 `null`，實際筆數與完整度必須重新查證。

## 7. 分析功能範圍

0. 展覽搜尋、新增與來源評估狀態（可取得方式、限制、完整度）。
1. 展會基本資訊、參展商結構與國家／產業分布。
2. 企業情報、別名與跨展會／跨年度身分整合。
3. 潛在客戶與商機排序。
4. 合作夥伴、代理商與通路機會。
5. 競爭對手與產品技術比較。
6. 競品可能展出內容（明確標示為預測）。
7. 技術、應用、能力、問題、需求與產業趨勢。
8. BXR 產品適配、展品組合與差異化建議。
9. 參展／參觀／不參加的決策與預算假設。
10. 必訪企業、洽談議題與已知展位資訊。
11. 跨展會、跨年度比較與定期市場報告。
12. 報告保存、來源追溯、重新分析及人工審核；以上分析都在 Web Dashboard 呈現，AI 推論一律標示，不得顯示為已查證事實。
13. 展後 CRM／成效回饋：比賽版預留結構，不強制完成整套 CRM。

BXR 產品範圍包含 AI XR SUT BOX、BXR POLICE BOX、GP-S、UAV／USV 相關模擬、RWG90、標槍模擬器及兵棋圖台；實際能力以經你確認的產品資料為準。

### 8.1 通用性驗收（必要）

**在不修改核心程式的前提下，系統能處理另一個不同展覽的資料，完成標準化、AI 分析及 Dashboard 展示。**

- 至少使用**兩組不同結構**的展覽資料（例如欄位、檔案格式或來源型態不同）測試通用性。
- 可以先用合成資料測試流程，但必須標示 `data_origin: "synthetic"`，畫面上也要標示；**正式成果（Phase 4）仍需至少一組真實、合法取得的公開資料驗證**。
- 驗收的是可重用的系統能力，不是完成特定展覽的名單；不得以任何展覽的參展商數量作為驗收指標。單一展覽或來源取得失敗時，記錄原因並改用其他來源，不阻礙階段驗收。
- 「不修改核心程式」的判斷：第二個展覽的 PR 只新增或修改展覽登錄資料、來源設定、來源適配器、匯入對應設定及資料檔，不修改 `etl/` 的標準化與驗證程式、`schemas/`、`skills/` 的分析邏輯或 `site/` 的頁面程式。
- 各階段的具體檢查項目見 [`DEVELOPMENT_PLAN.md`](DEVELOPMENT_PLAN.md) §6。

**每個階段的驗收與整合（你）：** 整合不阻擋任何人繼續開發。雙方都完成開發計畫中該階段的工作、PR 都已各自合併到自己的 dev 分支後，你取得兩條分支現況與 PR 清單，請 ChatGPT 產生該階段整合指令，由 Claude Code 在 `integration/phase-N` 整合、執行端到端測試（含 Dashboard 與截圖），你驗收通過後才更新 `main`。Phase 4 結束時建立競賽版 Release。

## 9. 工作項目、PR 與 Issue

- **一般工作不需要建立 Issue**，直接依 [`DEVELOPMENT_PLAN.md`](DEVELOPMENT_PLAN.md) 的工作項目開發。
- **Issue 只用於：** Bug、重大需求變更、跨人協調、需要追蹤的問題。既有的 Issue 保留為歷史紀錄。
- **每個可以獨立驗收的工作項目都要有 PR**，指向任務擁有者的 dev 分支，包含工作項目編號、變更摘要、測試命令與結果、Schema 相容性、限制、可視化成果（修改 `site/` 時附截圖或預覽）或執行日誌連結。
- 進度記錄在 [`PROGRESS.md`](PROGRESS.md)，由你依已合併的 PR 更新。

**單項 PR 的確認者是該項目擁有者；階段整合與驗收者才是你。** 若有跨人員規格衝突，暫停該工作項目，開 Issue 由你決定；不能各自修改規格後在最後碰運氣。

## 10. 競賽版不做與後續擴充

不強制：PostgreSQL、常駐 API、登入權限平台、完整 CRM、大規模商業級資料庫、全自動雲端 LLM 分析、複雜後台。Web Dashboard 是讀取版本化檔案的靜態 SPA，不屬於常駐 API 或複雜後台；網頁上的「新增展覽、觸發擷取、執行分析」在比賽版以 GitHub Actions 手動執行與 Claude Code 工作階段完成（§4.1），若要改成網頁一鍵執行，需你另行核准新服務。未來需要時再將檔案式儲存替換為資料庫，保持 `schemas/` 與 Skill 的資料讀取介面穩定。
